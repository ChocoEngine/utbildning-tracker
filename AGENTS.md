# Правила проекта Utbildning Tracker

Актуальные источники: [действующее ТЗ](docs/PRODUCT_SPEC.md),
[открытая работа](docs/OPEN_WORK.md), [уже проверено](docs/VERIFICATION_BASELINE.md),
[формат копии](docs/BACKUP_CONTRACT.md) и [запуск проверок](docs/TESTING.md).
Подробные старые отчёты и HTML-макеты удалены из рабочей копии; при
необходимости исходные результаты доступны в Git-истории.

## Состояние

- Работа ведётся в `codex/version-02` или её продолжении. Стабильную
  `codex/version-01` не изменять.
- R06 закрыт 2026-10-22 после подтверждения пользователем проверки на личных
  курсах. Для следующей версии эта проверка не засчитывается.
- Порядок: закончить U01–U03 и L01–L05, стабилизировать R07, затем передать
  сборку на новую полную пользовательскую проверку. S25 отложен до неё и
  запускается только по отдельному запросу.
- Готовые F01–F17 и PERF-01–07 не начинать повторно. Перенос отдельного
  занятия, сброс тем при изменении расписания и экран категорий в настройках
  исключены из ТЗ.

## Работа с кодом и данными

- Сверять правила с текущим кодом и поздними отчётами. Не принимать старый
  макет, план или имя теста за доказательство текущего поведения.
- Сохранять посторонние изменения. Перед кодовыми правками проверить рабочее
  дерево; не захватывать чужие файлы. Коммит и push — только по просьбе
  пользователя.
- При изменении экранов поддерживать RU/EN и Compose Preview. Для изменённой
  логики запускать релевантные тесты; итоговые полные проверки указаны в
  `docs/OPEN_WORK.md`. Успешная компиляция androidTest не означает выполнения
  instrumentation. Assumption-пропуск не считать пройденным тестом.
- Разрушительные тесты, импорт копии и полный instrumentation выполнять на
  тестовой базе/эмуляторе, не на единственной копии личных курсов. Для
  обновления приложения проверять установку поверх прежней версии без очистки.
- В отчётах различать найденное в коде, воспроизведённое на тесте и
  подтверждённое на работающем устройстве. Указывать точную ревизию,
  устройство/API, команды, результаты и непроверенные случаи.

## Документация

`docs/PRODUCT_SPEC.md` — единое ТЗ по текущим договорённостям.
`docs/OPEN_WORK.md` содержит только незавершённое и непроверенное. После
выполнения пункта обновлять его статус и ссылку на результат. Не добавлять
историю выполненных шагов в план: краткий проверенный результат заносить в
`docs/VERIFICATION_BASELINE.md`, а детали при необходимости сохранять вне
основной документации или искать в Git-истории. Изменение правила продукта сначала
зафиксировать в ТЗ, затем синхронизировать код и проверки.
