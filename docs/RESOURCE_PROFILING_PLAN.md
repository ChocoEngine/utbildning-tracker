Для нашего приложения я бы сделал **автоматический прогон на 2–3 часа**, отдельно измеряя память и файлы на диске. Просто оставить приложение открытым недостаточно — нужны повторяющиеся действия.

1. **Подготовить отдельный тестовый эмулятор API 36.**  
   Зафиксировать ревизию APK и загрузить синтетические данные: 10 активных курсов, много завершённых, по 500–1000 тем, длинную историю занятий. Личные курсы не использовать.

2. **Повторять сценарий 100–200 раз без перезапуска процесса:**
   - переходы «Сегодня → Календарь → Курсы → Настройки»;
   - открытие и закрытие редактора, прокрутка длинного списка;
   - изменение отметки темы;
   - сворачивание и возвращение;
   - периодические повороты экрана и смена RU/EN;
   - отдельными сериями — экспорт копии, проверка импорта и отмена.

3. **Каждые 30 секунд сохранять показатели:**
   
   ```sh
   adb -s emulator-5554 shell dumpsys meminfo -a com.utbildning.tracker
   adb -s emulator-5554 shell run-as com.utbildning.tracker du -ak .
   ```

   Дополнительно записывать PID, номер цикла и время. Если Android перезапустит процесс, это должно быть видно: перезапуск может скрыть накопление памяти. `dumpsys meminfo` показывает распределение памяти процесса. [Документация Android](https://developer.android.com/topic/performance/memory/guide/tools-overview).

4. **Снять heap dump после прогрева, в середине и в конце.**  
   Каждый раз возвращаться на один экран, давать приложению успокоиться и сравнивать состояние после GC. Искать оставшиеся уничтоженные `MainActivity`, старые редакторы, подписки и большие массивы. Для heap dump и записи Java/Kotlin allocations нужен **debuggable APK**; обычного profileable release недостаточно. [Android Profiler](https://developer.android.com/studio/profile), [анализ heap dump](https://developer.android.com/studio/profile/capture-heap-dump).

**Признак проблемы — устойчивый рост после одинаковых циклов и GC**, особенно вместе с накоплением объектов, которые уже должны освобождаться. Один высокий пик памяти или рост PSS сам по себе утечку не доказывает.

На диске отдельно проверять кеш, БД/WAL и внешние копии. Ручные копии намеренно сохраняются, поэтому их рост нужно учитывать отдельно. Прерывание экспорта с последующим запуском приложения — отдельный тест очистки временных файлов.

Большую часть такого прогона можно автоматизировать здесь через ADB и instrumentation; Android Studio нужен прежде всего для удобного разбора heap dump. Результат — графики памяти и диска, дампы и список подтверждённых удержаний. Даже успешный прогон будет проверкой выбранных сценариев, а не гарантией отсутствия любых утечек.
