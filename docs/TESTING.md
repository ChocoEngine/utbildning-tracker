# Проверки приложения

Текущий порядок и ещё не выполненные критерии итоговой версии — в
[плане](OPEN_WORK.md). Этот файл содержит команды и ограничения методов.

## Обычный прогон

JDK 17, Android SDK 36. Из `tracker-app/`:

```sh
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest :app:lintDebug :app:jvmCoverageReport --console=plain
./gradlew :app:connectedDebugAndroidTest --console=plain
```

Первый запуск собирает APK и выполняет JVM/lint; `assembleDebugAndroidTest`
только компилирует инструментальные тесты. Второй запуск выполняет их на
подключённом устройстве. Использовать отдельный тестовый AVD: тесты меняют
БД, язык, разрешения и уведомления. Перед полным прогоном нужна пустая тестовая
база: существующие демокурсы могут занять все цвета. Очистка допустима только
на выделенной тестовой копии; это не проверка обновления с сохранением данных.
Если подключено несколько устройств, выбрать одно через `ANDROID_SERIAL`.

Обычный прогон исключает классы с аннотациями `SystemScenario`,
`EmulatorFixture`, `ScreenshotCapture`. Они перечислены ниже и запускаются явно;
это не успешно пройденные регрессии. Проверки геометрии и взаимодействия,
которые также сохраняют снимки, остаются в обычном прогоне.

Число тестовых методов и набор пропусков
фиксировать по свежему отчёту, не по старому описанию. Assumption-пропуск не
считать успешной проверкой. Визуальные снимки требуют просмотра человеком.

Для утилиты оркестрации из корня репозитория:

```sh
tracker-app/gradlew -p tools/task-orchestrator test --console=plain
```

## Покрытие и назначение тестов

Основание для проверок — [ТЗ](PRODUCT_SPEC.md) и [контракт копии](BACKUP_CONTRACT.md).
Имена классов, методов, временных файлов и артефактов описывают поведение,
а не номера этапов. Тесты приложения не читают план и не проверяют его чекбоксы.
Тесты `task-orchestrator` проверяют сам парсер произвольных планов на
синтетических `T01`/`T02`, без зависимости от плана приложения.

Не дублировать чистую логику в Android-тесте без дополнительного наблюдаемого
контракта. JVM проверяет вычисления и формат архива; Room — транзакции,
ограничения и сохранность; Compose — действия и отображение; системные тесты —
фактическую доставку, переход и действия Android. Повторение одного правила
на разных границах оправдано, если проверяет их соединение.

`jvmCoverageReport` формирует HTML и XML в
`app/build/reports/jacoco/jvmCoverageReport/`. Область измерения явно ограничена
`domain/**`, `BackupArchive*`, `RetentionPolicy*`: это код, исполняемый JVM-тестами.
Проценты строк и ветвей **не являются покрытием всего приложения**. Room,
Compose, WorkManager, SAF и AlarmManager этим отчётом не измеряются.
Поведенческая матрица, результаты и оставшиеся границы — в
[аудите тестов](TEST_AUDIT.md). Для гарантированно свежего выполнения JVM-тестов
добавить `--rerun-tasks`; `UP-TO-DATE` означает повторное использование результата.

## Отдельные системные сценарии

`OvernightAlarmDeliveryTest` и `OpenMidnightTest` требуют запуска около
полуночи и исключены из обычного прогона. При явном запуске без нужных условий
они пропускаются по assumptions. Реальный reboot
и отзыв/возврат разрешений у `ReminderRecoveryTest` требуют внешних действий
между фазами `recovery_phase` (`prepare`, `denied`, `clicked_skipped`,
`cleanup`). Полный instrumentation сам по себе не доказывает доставку ночью,
работу после reboot или другую версию Android.

Для запуска исключённой группы указать `-PincludeAuxiliaryTests=true` и
**конкретный класс**; не включать все группы одним запуском. Например, после
подготовки часов выделенного AVD:

```sh
./gradlew :app:connectedDebugAndroidTest -PincludeAuxiliaryTests=true -Pandroid.testInstrumentationRunnerArguments.class=com.utbildning.tracker.ui.OpenMidnightTest --console=plain
```

### Выбор SAF-папки и перезапуск процесса

`SafBackupFolderTest` — отдельный `SystemScenario`. Из корня репозитория:

```sh
cd tracker-app
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest --console=plain
python3 scripts/test-saf-folder.py --serial emulator-5554
```

Указать выделенный тестовый AVD с исходными настройками копирования
(`automatic_backup` пуст); скрипт отказывается работать с физическим устройством.
Он устанавливает APK через `adb install -r`, не очищая БД. Python 3 и adb
берутся локально; путь к adb можно передать через `--adb`, новый каталог логов —
через `--logs`.

Фаза `prepare` создаёт собственный курс и UUID-папку через настоящее окно
DocumentsUI, выбирает её через приложение, проверяет постоянные права чтения
и записи, создаёт ручную копию кнопкой приложения и читает архив. Затем скрипт
выполняет `am force-stop`. Фаза `verify` проверяет новый процесс, сохранённую
папку и grant, читает прежнюю копию, меняет название тестового курса и создаёт
новую копию в той же папке без повторного открытия picker. Первая копия должна
остаться читаемой с прежним payload. Фаза `cleanup` удаляет только свои курс/папку,
освобождает grant и возвращает язык; выполняется и после ошибки предыдущих фаз.
После уборки скрипт ещё раз останавливает процесс и выполняет `check_cleanup`:
настройки копирования и служебный журнал должны остаться пустыми на диске.
Логи каждой фазы сохраняются отдельно, failures не определяются по коду adb
(он может вернуть 0 при упавшем тесте).

Это проверка локального `ExternalStorageProvider`, а не облачных провайдеров,
переноса между устройствами, reboot или полного восстановления БД. Обычный
прогон её исключает; запускать через скрипт, а не одну фазу вместо всего сценария.

`VisualReviewTest` и `TodayVisualReviewTest` с аннотацией `ScreenshotCapture`
только создают снимки. Их успешный запуск не доказывает правильность вида.
Снимки сохраняются в `Pictures/TrackerChecks` и требуют отдельного просмотра.

`EmulatorDemoSeedTest`, `EmulatorLongTitleSeedTest` и
`EmulatorAcceptanceSeedTest` с аннотацией `EmulatorFixture` — инструменты
наполнения, а не проверки. Вместе с конкретным классом и
`-PincludeAuxiliaryTests=true` передать соответствующий аргумент
`-Pandroid.testInstrumentationRunnerArguments.seedDemo=true`, `keepThreeDemo=true`,
`seedLongTitle=true` или `seedAcceptance=true` (с тем же префиксом).
Без аргумента они пропускаются. Не запускать заполнение и разрушительные сценарии на
единственной копии личных данных.

Для доказательства обновления поверх предыдущей версии установить APK через
`adb install -r` без очистки БД и сверить данные до/после. Для уведомления
наблюдать фактическую доставку и действие; факт регистрации alarm недостаточен.
Отчёт должен указывать ревизию, APK, API, локаль, конфигурацию экрана,
команды, success/failure/skip и ограничения.
