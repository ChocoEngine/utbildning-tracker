# Открытая работа и проверки

Актуально на 2026-10-29 для `codex/version-02` и её продолжения. Здесь только
незавершённое или не подтверждённое на будущей итоговой ревизии. Выполненные
MVP, F01–F17, PERF и R01–R06 не образуют повторную очередь. R06 закрыт после
проверки пользователя на личных курсах; следующая версия проверяется заново.
Результаты старых прогонов кратко сведены в [проверенной базе](VERIFICATION_BASELINE.md)
и доступны подробно в Git-истории; они не переносятся автоматически на
изменённую сборку.

Порядок: **R07 → полная проверка пользователя → S25**.
S25 запускается только по отдельному запросу после приёмки следующей версии.
Коммит, push, tag и публикация — по отдельному запросу.

L05 и изменение места хранения копий реализованы и проверены в
[проверенной базе](VERIFICATION_BASELINE.md). Продуктовые правила — в
[ТЗ](PRODUCT_SPEC.md), формат копии — в [контракте](BACKUP_CONTRACT.md).

## 1. R07 — инженерная стабилизация итоговой сборки

Ниже — план будущих прогонов, не результаты выполнения. Запуск не начат.
Объём: последняя версия на тестовых эмуляторах API 36 и API 33, без S25.
Выполнять последовательно: подготовка → сборка → обновление с сохранением
данных → полные наборы → направленные и системные сценарии → итог.

### R07.1. Зафиксировать сборку и подготовить окружение

- [ ] Перед запуском повторно проверить ветку и рабочее дерево. При первичной
  сверке: чистая `codex/version-02`, HEAD
  `fa1d3ef94b6b9d7890ee624335a2ab98e674f889`, `versionCode=1`,
  `versionName=0.1.0`. Во время подготовки плана появились параллельные
  изменения кода и тестов: перед прогонами зафиксировать их итоговый состав
  и нового кандидата, включая diff, если он ещё не закоммичен.
- [ ] Проверить JDK 17, SDK 36, свободное место и загрузку AVD. Локальные
  кандидаты JDK: `~/Library/Java/JavaVirtualMachines/temurin-17.0.13` и
  `jbr-17.0.9`; SDK: `~/Library/Android/sdk`. Записать фактически выбранные
  версии через `java -version` и `./gradlew --version`.
- [ ] Использовать отдельные тестовые AVD: для API 36 доступен `F17_API_36`;
  для API 33 найден образ и конфигурация `Pixel_6`, но тестовое назначение и
  содержимое ещё нужно проверить. Если там ценные данные, создать отдельный
  AVD на API 33. Не очищать неизвестную базу. Для сдвига часов использовать
  отдельный расходный AVD, не смешивая его состояние с проверкой обновления.
- [ ] Перед каждой серией записать AVD, serial, API/build, разрешение экрана,
  density, font scale, системную и выбранную в приложении локаль, часовой пояс,
  время и разрешения. При Gradle connected-прогоне подключать только целевой
  тестовый AVD; для отдельных adb-команд явно указывать serial.
- [ ] Подготовить отдельные каталоги результатов по кандидату/API/сценарию
  вне основных документов. Сохранять туда команды, логи, XML/HTML отчёты,
  снимки и сравнения данных до следующего прогона, который перезапишет отчёт.

### R07.2. Собрать один кандидат и проверить JVM/lint

- [ ] На JDK 17 и SDK 36 выполнить из `tracker-app/`:

  ```sh
  ./gradlew :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest :app:lintDebug --console=plain
  ```

- [ ] Сохранить app APK и test APK с SHA-256, ревизией и версиями. Один номер
  `0.1.0` не идентифицирует сборку. Все дальнейшие результаты связывать с этими
  файлами; после Gradle-прогонов проверять, что SHA-256 не изменился.
- [ ] Разобрать ошибки сборки, JVM и lint; записать предупреждения. Компиляцию
  androidTest учитывать отдельно от выполнения тестов.

### R07.3. Обновление поверх предыдущей версии — API 36 и API 33

- [ ] До разрушительных тестов подготовить на каждом API предыдущий APK
  известного происхождения, совместимой подписи и с зафиксированным SHA-256.
  Сначала искать сохранённый APK; если его нет, собрать прежнюю ревизию в
  отдельном checkout, не меняя стабильную ветку и рабочую копию кандидата.
  Зафиксировать выбранную исходную ревизию и версии Room до/после.
- [ ] В прежней версии создать синтетический набор: категории, курсы с темами
  и без, отмеченные темы, результаты занятий, активный/приостановленный/
  завершённый курс, расписание с конечной датой и ночным окончанием. Настроить
  язык, хранение истории, папку копий и недельное копирование; сохранить копию
  и снимок переносимых данных и локальных настроек.
- [ ] Установить кандидат через `adb -s SERIAL install -r CANDIDATE.apk`,
  без удаления приложения, очистки данных и импорта. Сверить поля и связи,
  настройки, доступ к прежней папке, историю и прогресс до/после; учесть только
  объяснимые изменения от синхронизации дат. Повторить сверку после холодного
  запуска и проверить отсутствие дублей занятий и задач копирования.
- [ ] Проверить сохранность системных разрешений и пользовательского выбора
  напоминаний, пересчёт alarm. Не считать установку поверх текущей сборки
  доказательством обновления со старой. Если схема одинакова, отдельно указать,
  что обновление проверено без миграции; миграции покрыть тестами полного набора.

### R07.4. Полный instrumentation — отдельно на API 36 и API 33

- [ ] После сохранения результатов обновления подготовить тестовую базу и
  выполнить на каждом API из `tracker-app/`:

  ```sh
  ./gradlew :app:connectedDebugAndroidTest --console=plain
  ```

- [ ] Для каждого API сохранить фактические success/failure/skip и причины
  каждого пропуска. Проверить, что набор действительно выполнен; отсутствие
  failures при нуле тестов или assumption-пропуске не считать успехом.
  Демо-seed без явных аргументов может быть пропущен: это утилита подготовки,
  а не подтверждение сценария. Полночь и recovery закрывать отдельными сериями.
- [ ] Каждый failure воспроизвести и разобрать. После исправления повторить
  затронутый сценарий; при изменении приложения собрать нового кандидата,
  обновить SHA-256 и повторить полный набор на обоих API. Итоговую приёмку
  выполнять на финальном APK, не собирать её из результатов разных версий.

### R07.5. Направленная проверка продукта и последних изменений

- [ ] На обоих API пройти создание/редактирование курса, категории, темы и
  прогресс, расписание с включительной конечной датой, запрет прошлой даты,
  ночное окончание, предупреждение пересечений, календарь, сегодня/вчера и
  ограничения изменения старого/будущего занятия. Проверить паузу/продолжение,
  завершение/перезапуск и холодный запуск без дублей. Сопоставить с результатами
  существующих UI/repository-тестов, вручную дополнить непокрытые пути.
- [ ] На обоих API визуально пройти RU/EN настройки и гайд, включая нижние
  действия, диалоги, клавиатуру и длинный путь папки. На API 36 дополнить узким
  экраном 360×800 dp и `font_scale=1.3`, как в предыдущей проверке L05.
  Полную матрицу TalkBack/контраста/масштабов S25 здесь не начинать.
- [ ] Проверить единый переключатель напоминаний: последовательные системные
  запросы, отказ, возврат из настроек Android, выключение с отменой уже
  показанных уведомлений и повторное включение с сохранёнными разрешениями.
- [ ] На обоих API проверить ручную копию в папке по умолчанию и выбранной
  через SAF, отмену выбора, длинный вложенный путь и возврат к умолчанию.
  Два контролируемых запуска weekly worker должны оставить новую проверенную
  копию, удалить прежнюю недельную и сохранить ручной файл. Проверить отказ
  доступа/записи без потери предыдущей копии и восстановление после возврата
  доступа; сохранить результаты `AutomaticBackupTest`.
- [ ] На тестовых данных пройти экспорт → изменение → импорт с подтверждением
  полной замены → холодный запуск и сверку данных/языка. Отмена, повреждение и
  неподдерживаемая версия не меняют БД. Синтетический v1-эталон не называть
  реальным экспортом старой версии. Проверить границу очистки истории и
  сохранность курсов/тем; использовать существующие тесты/контролируемый worker.

### R07.6. Системные сценарии — отдельно на каждом API

- [ ] При обычном времени и включённых напоминаниях дождаться настоящих alarm
  начала и вопроса об итоге. Выполнить `LocalizedReminderDeliveryTest`,
  `ReminderNavigationTest` и `NotificationShadeResultTest`: RU/EN, сегодня/вчера,
  с темами/без, тело уведомления и обе кнопки. Зафиксировать фактическую
  доставку, переход и результат в БД, включая защиту от устаревшего действия.
- [ ] Выполнить реальный reboot через adb между фазами `ReminderRecoveryTest`:
  `prepare` → reboot → завершение загрузки/разблокировка → ожидание доставки →
  действие «Пропущено» → `clicked_skipped` → `cleanup`. Тест планирует старт
  примерно через три минуты: убедиться, что reboot укладывается в окно и
  отдельно дождаться вопроса с кнопкой результата; при необходимости создать
  короткое тестовое занятие. Проверить данные и отсутствие дублей/alarm после
  перезапуска; один обычный запуск recovery-теста reboot не проверяет.
- [ ] В отдельных циклах `prepare` проверить отзыв и возврат уведомлений и
  точных сигналов, а также обоих разрешений: `denied` при отказе, сохранность
  данных и доступность календаря, восстановление планирования после возврата,
  новая реальная доставка и `cleanup`. Проверить также выключенный пользователем
  переключатель: возврат системных разрешений не должен сам включить напоминания.
- [ ] На расходном AVD подготовить локальное время 23:59 с секундами <45 и
  выполнить `OpenMidnightTest`: дождаться перехода полуночи при открытом экране,
  проверить «Вчера», догоняющий SKIPPED и отсутствие дублей. Подготовку часов
  завершить до запуска; не заменять ожидание синтетическим `TIME_SET`.
- [ ] Отдельно подготовить 00:57–00:59 и выполнить `OvernightAlarmDeliveryTest`:
  дождаться реального alarm в 01:00 для 23:30→01:00 и 23:30+90 минут,
  проверить результаты DONE/SKIPPED. Этот тест создаёт вчерашние занятия перед
  доставкой: он не доказывает непрерывное ожидание от начала до конца ночи.
  Дополнительно провести короткое занятие через полночь: получить начало до
  00:00 и вопрос после, затем проверить действие шторки и запись результата.
- [ ] Записать способ подготовки RTC, локальное время и реальные интервалы
  ожидания. После серии вернуть обычное время/автосинхронизацию и настройки
  экрана/разрешений; не переносить сдвинутые часы в остальные прогоны.

### R07.7. Итог и границы приёмки

- [ ] Свести матрицу API 36/API 33 по всем сериям: ревизия, SHA-256 обоих APK,
  устройство, экран, язык, время, команды, успехи, failures, skips, ссылки на
  артефакты, подтверждённые дефекты и непроверенные случаи. Краткий результат
  внести в [сводку проверок](VERIFICATION_BASELINE.md), выполненные пункты
  убрать из открытого плана, оставив ссылку на результат.
- [ ] Отдельно обозначить ограничения: эмулятор не подтверждает физическое
  устройство/прошивки производителей, облачный SAF и перенос между устройствами.
  Контролируемый запуск worker не доказывает реальное семидневное ожидание
  копии или суточное ожидание очистки; такие ожидания не включены в этот прогон.
- [ ] Закрыть R07 только после успешных инженерных проверок обоих API,
  сохранности данных при обновлении и отсутствия подтверждённых критичных
  дефектов основных сценариев. Незакрытый обязательный системный сценарий
  оставить открытым с причиной, а не засчитать по старому результату.
  Подготовить финальный APK с перечнем изменений и ограничений для следующего
  этапа. Личная пользовательская приёмка остаётся отдельной; S25 отложен.

## 2. Независимая полная проверка пользователя

Проводится **после** U/L и R07 на конкретной переданной сборке. Проверка R06
относилась к прежней версии и не заменяет этот этап.

- [ ] Передать APK, ревизию, номер версии, перечень изменений и ограничения;
  записать установленную сборку и устройство/API.
- [ ] На личных курсах проверить создание и редактирование, категории, темы,
  расписание/конечную дату, отметку и исправление занятия, календарь,
  паузу/продолжение, язык и гайд. Перезапуск завершённого курса и
  восстановление с полной заменой данных проверять на отдельной базе либо
  после сохранённой копии и явного выбора пользователя.
- [ ] Проверить несколько реальных занятий, включая уведомление и ночное
  занятие либо оставленное до следующего дня. Записать фактически выполненное,
  ожидание, результат и замечания; пропущенные случаи оставить непроверенными.
- [ ] После исправления замечания передать новую сборку, повторить затронутый
  сценарий и получить явное подтверждение пользователя для этой версии.

## 3. S25 — отложенная доступность

До полной пользовательской проверки следующей версии S25 не начинать.
После отдельного запроса в изолированной ветке/checkout проверить и при
необходимости исправить:

- [ ] TalkBack на всех экранах, диалогах и списках: понятные имена, роли,
  состояния и порядок фокуса. Прогресс озвучивать как число завершённых тем,
  а у курса без тем — занятий; день календаря — с полной датой, выбором и
  кратким содержимым, строку занятия — с курсом, временем и результатом.
  Ошибку ввода связать с полем; после диалога возвращать фокус к действию или
  ближайшему логическому элементу. Цвет не должен быть единственным сигналом.
- [ ] Именованные действия темы без удержания для TalkBack/Switch Access и
  клавиатурный Enter/Space с одним изменением на нажатие, без переключения от
  автоповтора. Обычный короткий тап не отмечает тему; долгое касание остаётся,
  прокрутка его отменяет. Категории и календарь доступны без сложных жестов.
- [ ] Зоны нажатия от 48×48 dp без перекрытия, включая календарную сетку,
  карандаш категории, удаление даты, цвета и кнопки диалогов. Проверить
  100/150/200% шрифт и увеличенный системный размер на узком экране с IME:
  текст не перекрывает действия, диалоги прокручиваются, кнопки достижимы.
- [ ] Контраст текста не ниже 4.5:1, крупного текста и важных графических
  элементов не ниже 3:1; состояния различимы без цвета.
- [ ] Автоматические регрессии именованных действий темы, календарного дня и
  категории с тем же результатом данных, что при обычном взаимодействии.
  Вручную пройти RU/EN с TalkBack и отдельно клавиатурой/Switch Access:
  курс, категорию (добавление без выбора, выбор, удаление), расписание,
  календарь, отметку темы и занятия, подтверждение/отмену завершения, язык
  и гайд. Проверить API 36 и минимальный API 33 либо явно оставить API 33
  непроверенным. В [сводке](VERIFICATION_BASELINE.md) записать устройство,
  версии сервиса, язык, масштаб, сценарии, контраст и ограничения; при
  необходимости приложить новые снимки.

S25 не является условием закрытия R07. Существующую доступность не ухудшать.

## 4. Отложенное профилирование памяти и диска

- [ ] По отдельному запуску выполнить [сохранённую схему профилирования](RESOURCE_PROFILING_PLAN.md).
  Схема записана дословно из обсуждения 2026-10-29. Выполнение отложено:
  дата не назначена, автозапуск и напоминания не создаются по выбору пользователя.
  После выполнения записать ревизию, окружение, результаты и ограничения
  в [сводку проверок](VERIFICATION_BASELINE.md).
