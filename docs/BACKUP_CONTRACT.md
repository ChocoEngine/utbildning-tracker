# Резервная копия и восстановление

Статус: контракт F01, реализация F02–F04; переносимая модель соответствует Room
v7, текущая Room v8 добавляет только неэкспортируемый служебный `backup_state`.
Этот документ определяет формат и гарантии. Ручной экспорт F02, безопасный
импорт F03 и UI восстановления F04 реализованы; фоновые копии остаются в F05
в [FEATURE_PLAN.md](../FEATURE_PLAN.md).

## Цель и границы

Резервная копия переносит пользовательские данные приложения целиком. Импорт
всегда заменяет текущий набор данных после явного подтверждения; объединения,
выбора отдельных курсов и частичного восстановления нет. Исходный файл при
импорте не изменяется.

Формат не является копией файла SQLite. Он не зависит от внутренних имён
индексов и миграций Room и может быть проверен до открытия транзакции записи.
Первая версия не шифрует данные: файл содержит названия курсов, тем и историю
занятий в читаемом виде. Хеш защищает от случайного повреждения, но не является
подписью и не доказывает авторство файла.

## Контейнер v1

- Расширение: `.studytracker-backup`.
- MIME: `application/vnd.utbildning.tracker.backup+zip`.
- Контейнер ZIP содержит ровно два обычных файла в корне: `manifest.json` и
  `data.json`. Каталоги, абсолютные пути, повторяющиеся имена, ссылки и
  зашифрованные ZIP-entry запрещены.
- Оба JSON-файла кодируются UTF-8 без BOM. Дубли ключей JSON, нецелые значения
  для целочисленных полей и значения вне диапазона `Long` запрещены.
- Максимальный размер контейнера — 50 MiB, `manifest.json` после распаковки —
  64 KiB, `data.json` после распаковки — 50 MiB. Проверка ведётся потоково по
  фактически распакованным байтам, поэтому заявленный ZIP-размер ей не доверяется.
- Экспорт сначала создаёт и повторно проверяет завершённый файл во внутреннем
  временном каталоге приложения. Только после этого файл копируется в выбранное
  пользователем место. Неудачная запись никогда не объявляется успешной и не
  удаляет прежнюю успешную копию.

`manifest.json` имеет следующий обязательный каркас:

```json
{
  "format": "utbildning-tracker-backup",
  "formatVersion": { "major": 1, "minor": 0 },
  "backupId": "4c5a8cc4-9218-4f95-84ea-c46f32430b3a",
  "createdAt": "2026-10-07T12:00:00Z",
  "app": { "versionCode": 1, "versionName": "0.1.0" },
  "databaseSchemaVersion": 8,
  "requiredFeatures": [],
  "payload": {
    "path": "data.json",
    "bytes": 1234,
    "sha256": "64 lowercase hexadecimal characters"
  }
}
```

`payload.bytes` и SHA-256 считаются по точным распакованным байтам `data.json`.
`databaseSchemaVersion` и версия приложения служат диагностикой и не определяют
способ импорта: его определяет только версия формата. `backupId` — UUID новой
копии, `createdAt` — UTC RFC 3339 с обязательным часовым поясом.

## Полезная нагрузка v1

Верхний уровень `data.json`:

```json
{
  "settings": { "languageTag": "ru" },
  "categories": [],
  "courses": [],
  "topics": [],
  "schedules": [],
  "scheduleRules": [],
  "sessions": []
}
```

Порядок массивов не имеет смысла. Экспортёр записывает их детерминированно по
первичным ключам, чтобы одинаковый снимок было проще сравнивать. Все ID — строки;
даты хранятся как epoch day, время суток — минутой `0..1439`, временные метки —
epoch milliseconds. `null` записывается явно для необязательных полей.

| Массив | Поля v1 | Что сохраняется |
|---|---|---|
| `categories` | `id`, `name` | Все категории, включая пока не используемые курсами. |
| `courses` | `id`, `name`, `colorId`, `createdAt`, `updatedAt`, `categoryId`, `isCompleted`, `isPaused`, `completedAt` | Состояние курса, категория, цвет и завершение. |
| `topics` | `id`, `courseId`, `position`, `title`, `isCompleted`, `completionDate` | Список, порядок и текущий источник прохождения темы. Отдельных исторических таблиц прохождения в v7 нет. |
| `schedules` | `courseId`, `startsOn`, `endsOn`, `generatedThrough` | Границы правила и достигнутый генератором горизонт. |
| `scheduleRules` | `courseId`, `dayOfWeek`, `startMinute`, `endMinute` | Недельные правила; окончание раньше начала означает следующие сутки согласно действующему контракту. |
| `sessions` | `id`, `courseId`, `date`, `startMinute`, `createdAt`, `updatedAt`, `endMinute`, `result` | Полная календарная история и результаты `PENDING`, `DONE`, `SKIPPED`. |

`settings.languageTag` принимает `""` (язык системы), `"ru"` или `"en"`.
Это единственная переносимая пользовательская настройка текущей версии.
Добавляемые позднее настройки резервного копирования и срока хранения должны
получать отдельные необязательные поля с безопасным значением по умолчанию.

### Что не входит в копию

- разрешения Android, специальный доступ exact alarm и состояние системных
  notification channels;
- URI выбранного места хранения и выданные провайдером права доступа к нему;
- служебный `settings.notification_requested`;
- активные уведомления, зарегистрированный `AlarmManager` alarm и множество
  `reminders.delivered`;
- кэши, журналы, временные файлы, индексы SQLite и внутреннее состояние
  восстановления;
- демонстрационные и instrumentation-настройки.

Эти значения зависят от устройства или вычисляются заново. После успешного
импорта runtime-состояние напоминаний очищается, выполняются синхронизация и
`ReminderScheduler.reconcile()`. Системные разрешения остаются такими, какими
они были на принимающем устройстве; при отсутствии доступа приложение просит
его обычным способом. Недавнее событие в пределах действующего пятиминутного
окна может один раз напомнить снова, поскольку история доставки не переносится.

## Согласованный экспорт

1. Прочитать язык приложения и начать read-транзакцию Room.
2. В одной транзакции прочитать все шесть таблиц. Записи, сделанные после начала
   снимка, в него не входят; ни один курс не может попасть без связанных данных
   из другого момента.
3. После транзакции повторно прочитать язык. Если он изменился, снимок отбросить
   и повторить один раз; при повторной гонке вернуть ошибку, не создавая файл.
4. Сериализовать неизменяемый снимок во внутренний временный файл, вычислить
   размер и SHA-256, собрать контейнер и полностью проверить его тем же
   валидатором, который используется при импорте.
5. Передать готовые байты в выбранный пользователем новый документ. Успех
   показывается только после закрытия потока и повторной проверки доступного
   результата. Отмена и ошибка не меняют БД и настройки.

Долгую сериализацию и запись нельзя выполнять внутри Room-транзакции. Экспорт не
копирует открытый `tracker.db`, WAL или SHM отдельно.

## Проверка перед восстановлением

До изменения рабочих данных импорт обязан полностью проверить:

1. ограничения и безопасные имена ZIP-entry, magic `format`, поддерживаемую
   версию, `requiredFeatures`, UUID, размер и SHA-256 payload;
2. обязательные поля и типы JSON; неизвестные обязательные возможности;
3. уникальность всех первичных и составных ключей;
4. ссылки: `courses.categoryId` указывает на категорию либо `null`; тема и
   занятие относятся к существующему курсу; расписание относится к курсу;
   правило относится к существующему расписанию;
5. ограничения текущей модели: непустые ID и названия, диапазон цвета `0..9`,
   времени `0..1439`, дня недели `1..7`, неотрицательную позицию темы,
   `endsOn >= startsOn`, допустимый `SessionResult`, согласованность
   `isCompleted`/`completedAt`/`colorId` и `completionDate == null` у
   непройденной темы;
6. не более десяти незавершённых курсов и уникальность их ненулевых цветов;
   уникальность занятия по `(courseId, date, startMinute)`;
7. возможность построить все Room-сущности без исключения.

Импорт не применяет новые UI-ограничения задним числом к старым корректным
данным: например, уже существующая длинная тема должна восстановиться без
обрезки. Никакие строки не исправляются автоматически, потерянные ссылки не
отбрасываются, конфликтующие ID не перенумеровываются. Любая ошибка отклоняет
весь файл с понятной причиной до запроса на замену данных.

## Полная замена и восстановление после сбоя

После успешной проверки UI показывает краткое подтверждение полной замены.
Только после подтверждения начинается изменение состояния:

1. Записать во внутренний долговечный журнал `PREPARED` с `backupId`, хешем и
   целевыми переносимыми настройками. Запись журнала сама атомарна.
2. В одной Room-транзакции удалить пользовательские таблицы в порядке
   `sessions` → `schedule_rules` → `schedules` → `topics` → `courses` →
   `categories`, вставить их в обратном порядке зависимостей и записать
   внутренний `committedBackupId = backupId`.
3. После commit применить язык, очистить производное состояние напоминаний,
   отменить старые alarm/уведомления, выполнить синхронизацию и построить
   актуальные напоминания.
4. Только после успешных пост-действий удалить журнал и показать успех.

`committedBackupId` и журнал — служебные данные реализации, они не экспортируются.
При запуске после прерывания приложение сравнивает их:

- если ID не совпадают, транзакция замены не была зафиксирована; Room оставил
  прежние данные целиком, журнал удаляется;
- если ID совпадают, новый набор данных уже записан целиком; приложение
  идемпотентно завершает настройки и сверку напоминаний, затем удаляет журнал.

Таким образом, ни ошибка записи, ни исключение, ни остановка процесса не могут
оставить смесь старых и новых строк. До commit старые alarm не отменяются.
Короткое окно после commit безопасно: receiver всё равно перечитывает актуальные
данные, а незавершённые пост-действия повторяются при следующем запуске.

## Совместимость и развитие

- Текущий reader принимает `major = 1`, известные обязательные поля и только те
  элементы `requiredFeatures`, которые он реализует. Неизвестная обязательная
  возможность или другой major отклоняются без изменения данных.
- Увеличение minor разрешено для необязательных полей с определённым значением
  по умолчанию. Неизвестные необязательные поля игнорируются и сохранять их при
  следующем экспорте не требуется.
- Новая сущность или правило, потеря которого меняет смысл данных, добавляется
  как `requiredFeature`; несовместимое изменение повышает major.
- Экспорт всегда пишет последнюю поддерживаемую версию. Импорт v1 обязан
  поддерживаться последующими версиями приложения через явное преобразование
  DTO, а не через запуск старой Room-схемы.
- Копии, созданные более новой версией, не обещают восстановление в старой.
  Версия БД сама по себе не является основанием принять или отклонить файл.

## Критерии реализации F02–F04

- Круг `экспорт → проверка → импорт` сохраняет все перечисленные строки, ID,
  связи, результаты, порядок тем, цвета, расписания, язык и временные значения.
- Параллельное редактирование даёт снимок до или после транзакции, но не смесь.
- Повреждение любого байта payload, лишняя/опасная ZIP-entry, неподдерживаемая
  версия, неверная ссылка или нарушение ограничения отклоняются до замены.
- Исключение в середине Room-транзакции оставляет прежние данные; остановка после
  commit завершается при следующем запуске.
- Повтор незавершённого post-commit шага идемпотентен и не создаёт дубли занятий
  или уведомлений.
- Отмена выбора файла и отказ от подтверждения ничего не меняют.
- Проверки используют отдельные тестовые данные, а не единственную копию личных
  курсов пользователя.
