# После MVP: отладка и развитие

Актуальные уточнения редактора и списков после ручной проверки — [COURSE_UI_REVISION.md](docs/COURSE_UI_REVISION.md), задачи U01–U04. Эти правила заменяют прежнее общее сохранение курса; начатая реализация ещё не принята.

## Приоритет и правила исполнения

Сначала отладить существующую функциональность, затем добавлять новые возможности. S25 вести отдельной параллельной версией; он не входит в приёмку основной функциональной версии. Этот документ планирует работу, а не утверждает, что ревизия уже выполнена.

Команда «Выполни следующий шаг после MVP» означает один первый незавершённый шаг R01–R06 ниже. Читать AGENTS.md, этот план и относящиеся к шагу контракты; не перечитывать весь проект. Не запускать S25 или новые функции по этой команде. Для частичного шага дописывать оставшуюся работу. Ставить `[x]` только после проверки критериев и ссылки на отчёт; синхронизировать краткий статус в AGENTS.md. Не делать попутный рефакторинг, обновление стека, коммиты или push без отдельного запроса.

## Основная версия: ревизия и отладка

По существующему чек-листу MVP реализация и проверки API 36 завершены, но S01/S20 частичны из-за отложенного Android 13, S24 — из-за непроверенной скруглённой квадратной маски. Это исходные сведения из документов, не результат новой ревизии. Не закрывать эти пункты по прежним тестам другого устройства и не отменять отсрочку Android 13 самостоятельно.

- [ ] **R01 — Ревизия без изменения кода.** Сверить `MVP_PLAN.md`, `docs/DATA_CONTRACT.md`, `docs/SCHEDULE_CONTRACT.md`, `docs/NOTIFICATIONS.md`, `docs/checks/mvp/README.md` и `docs/checks/s24/README.md` с относящимся к ним кодом в `tracker-app/`. Проверить основной путь UI → ViewModel → репозиторий → Room, а не только наличие файлов. Запустить доступные текущие проверки. Создать `docs/review/MVP_REVIEW.md`: для каждого дефекта ID, важность, ожидаемое/фактическое поведение, точный файл/место, воспроизведение или доказательство из кода, способ проверки исправления. Разделить подтверждённые дефекты, предположения и непроверенные сценарии. Критерий: получен конкретный список, код не изменён; отсутствие замечаний допустимо, придумывать дефекты не нужно.
- [ ] **R02 — Исправить дефекты данных и бизнес-правил.** По одному дефекту или тесно связанной группе из R01. Сначала воспроизводящая проверка, затем минимальное исправление и повторная проверка. Приоритет: потеря/порча данных, ошибочное прохождение темы, дубли занятий, неправильное завершение/пауза/удаление. Проверить ручную отметку и исправление занятия в разных порядках, одинаковые названия тем, сохранение ID при редактировании, снятие отметки, исчерпание/добавление тем, лимит и освобождение цвета, удаление категории без удаления курсов. Основные области — `tracker-app/app/src/main/java/com/utbildning/tracker/data/` и `domain/`. Не добавлять новых режимов. Критерий: связанные подтверждённые дефекты закрыты доказательствами в отчёте; если дефектов нет, отметить это и не менять код.
- [ ] **R03 — Отладить даты и уведомления.** Проверить генерацию после долгого отсутствия, смену суток при открытом приложении, границы месяца/года, конец расписания, часовой пояс и повторный запуск. Для уведомлений — реальная доставка/переход, отмена после изменения курса, перезагрузка, отказ/отзыв разрешений. Исправлять только подтверждённые дефекты, сохранять зафиксированную политику времени из контрактов. Области — `domain/`, репозиторий, `notifications/` и экраны времени. Критерий: повторные операции не меняют уже заданные результаты, не создают дубли и лишние уведомления; указаны реально проверенные API и оставшиеся ограничения. Не повторять дорогие системные проверки без изменения затрагивающего кода или сомнения в старом результате.
- [ ] **R04 — Функциональная и визуальная приёмка.** Сверить экраны с последними продуктовыми правилами и `design/mockups/README.md`; старые макеты не отменяют более поздние решения. Пройти создание/редактирование курса и категории, массовый список тем, отмену форм и диалогов, выбор/очистку даты, отметки и исправления, фильтр завершённых, оба режима курса. Проверить RU/EN, длинные названия, прокрутку, открытие клавиатуры, возврат назад, перезапуск и сохранение черновиков согласно контракту. Исправить функциональные ошибки UI и явные расхождения с согласованным дизайном. Критерий: сценарии пройдены, снимки и результаты приложены к отчёту. Полный аудит TalkBack, контраста и масштабирования S25 сюда не входит; уже работающую доступность не ухудшать.
- [ ] **R05 — Проверка пользователем на своих курсах.** Подготовить актуальный debug APK, записать путь, версию и известные ограничения; предоставить короткий список действий для самостоятельной проверки. Рекомендуемый период — несколько реальных занятий, включая одно с уведомлением. Замечания собирать в том же отчёте: шаги, ожидание, результат, при необходимости снимок. Не планировать автоматические напоминания и не ждать несколько дней внутри одной задачи. Критерий: пользователь подтвердил прохождение проверки, замечания разобраны; отсутствие ответа не означает успех. Исправления возвращаются в R02–R04 по области.
- [ ] **R06 — Зафиксировать стабильную функциональную версию.** После исправлений выполнить итоговые сборку, lint, JVM- и инструментальные тесты; проверить обновление поверх предыдущей сборки с сохранением данных, без удаления приложения и сброса БД. Сохранить отчёт `docs/checks/stabilization/README.md`: конкретная ревизия/состав изменений, версии, устройство/API, результаты и ограничения. Список подтверждённых критичных дефектов и дефектов основных сценариев должен быть пуст. Android 13 и маску иконки оставить явно непроверенными, если ограничения всё ещё действуют; не объявлять проверенными все поддерживаемые устройства. Критерий: основной функционал принят пользователем, данные сохраняются при обновлении, проверки пройдены в заявленном окружении. Коммит/tag/публикация требуют отдельного запроса.

### Команды проверок

Из `tracker-app/`, с окружением из `tracker-app/README.md`:

```sh
./gradlew :app:assembleDebug :app:lintDebug :app:testDebugUnitTest
./gradlew :app:connectedDebugAndroidTest
```

Инструментальные тесты выполнять на тестовом устройстве/профиле, не на единственной копии личных курсов. Перед тестом проверить, не очищают ли фикстуры данные. Для локального исправления достаточно релевантных тестов и сборки; полный прогон — при итоговой приёмке или необходимости проверить регрессию. Тесты не подменяют фактическую доставку уведомления и ручную приёмку.

## Параллельная версия S25

S25 — отдельная линия разработки доступности на общей кодовой базе, а не новый продукт с независимой бизнес-логикой. Детальные задачи остаются в [ACCESSIBILITY_PLAN.md](docs/ACCESSIBILITY_PLAN.md).

1. Сейчас приоритет R01–R06; автоматически работу над S25 не начинать. После отладки основной функциональности, по отдельному запросу, создать из её зафиксированного состояния отдельную ветку/изолированный checkout для S25. Этот план сам по себе не создаёт веток или параллельных задач.
2. Изменения S25 не должны попадать в основную отлаживаемую версию до отдельной приёмки. Не копировать репозиторий внутрь проекта и не создавать вторую реализацию Room, расписания или прогресса.
3. Исправления общих функциональных дефектов сначала вносить и проверять в основной линии, затем переносить в S25. Проблему общей логики, найденную при S25, записывать в основной отчёт, а не исправлять только в параллельной версии.
4. Если потребуется установить обе сборки на один телефон, для проверочной версии S25 задать отдельный applicationId и понятный суффикс названия. Она использует отдельные тестовые данные; не подключать обе версии к одной БД. Не добавлять постоянный продуктовый flavor без этой необходимости. До установки проверить идентификаторы, чтобы не заменить основную сборку случайно.
5. Приёмка S25 включает его собственные ручные проверки и регрессию функциональности R02–R04. После приёмки объединение с основной версией обсуждается отдельно; автоматически сливать или выпускать параллельную сборку не нужно.

## Развитие после стабилизации

Подробные задачи F01–F18, критерии, чек-лист и открытые вопросы — в [FEATURE_PLAN.md](FEATURE_PLAN.md). Команда «Выполни следующий шаг функционального плана» выполняет один шаг F после стабилизации R01–R06. Это отдельная очередь от команды «следующий шаг после MVP», которая относится только к ревизии R01–R06. Состав функций сохранён из DEVELOPMENT_PLAN.md, приоритет хранения уточнён: резервная копия до автоматической очистки.

1. **Сохранность данных:** ручной экспорт и восстановление с полной заменой после подтверждения; затем еженедельные копии, выбранное место и статус последней успешной копии. Проверить повреждённые файлы, совместимость схем, отказ в доступе, восстановление расписаний и уведомлений.
2. **Пауза и возобновление:** согласовать компактное обозначение в списке и восстановление расписания без потери истории.
3. **Гибкое расписание:** перенос одного занятия; затем замена расписания с выбором продолжения или сброса тем. Перед разрушительной заменой явно показать последствия и проверить сохранность резервной копии.
4. **Возврат и смена режима:** повторная активация завершённого курса с проверкой лимита/цвета; переключение «по расписанию / без расписания». До реализации согласовать судьбу истории при отключении расписания.
5. **Очистка истории:** сохранять итоговую статистику отдельно; затем настраиваемая очистка календаря завершённого курса, по умолчанию через 10 дней без изменений, с отключением. Реализовать после проверенного восстановления из копии.
6. **Необязательные улучшения:** пересечения расписаний, фильтры, дополнительные напоминания и виджет — только по результатам использования и отдельному выбору пользователя. Заметки, достижения и серии занятий не добавлять.

Следующее действие: **R01 — ревизия без изменения кода**. Составление этого плана не запускает ревизию или S25.
